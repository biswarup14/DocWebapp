# Domain migration

How to move the site to a different domain without losing search ranking, and
where the domain lives in code.

## Where the domain is defined

**`src/config/site.js`** — one file, one constant:

```js
export const SITE_URL = 'https://dentalcarebest.in';
```

Everything that emits an absolute URL derives from it:

| Output | Mechanism |
| --- | --- |
| Canonical, hreflang, `og:url`, OG/Twitter image, all JSON-LD `@id`s | `src/components/SEO/SEO.jsx` imports `SITE_URL` |
| Static head in `index.html` | `__SITE_URL__` token, replaced at build time by `build/seo-assets.js` |
| `sitemap.xml` | Generated by `build/seo-assets.js` from `INDEXABLE_ROUTES` |
| `robots.txt` `Sitemap:` line | Generated by `build/seo-assets.js` |
| `dist/_redirects` | Generated by `build/seo-assets.js`; **no active rules** — host moves go in a zone-level Cloudflare Redirect Rule, trailing slashes are handled by `html_handling` |

`sitemap.xml` and `robots.txt` are **build artifacts, not source files**. Do not
recreate them under `public/` — they are generated into `dist/` and would then
be duplicated. To add or remove a page, edit `INDEXABLE_ROUTES` in
`src/config/site.js`.

`src/config/site.test.jsx` fails the build if the domain string reappears
anywhere else, and if a sitemap entry drifts from the canonical that `<SEO>`
renders. Run it with `npm run test`.

## Migration steps

### 1. Change the code

```js
// src/config/site.js
export const SITE_URL = 'https://new-domain.com';

// The retired origin. Recording it blocks the build until you confirm the
// zone-level redirect in step 3.
export const PREVIOUS_SITE_URL = 'https://old-domain.com';

// Flip to true only after step 3 is live and verified.
export const HOST_REDIRECTS_CONFIRMED = false;
```

If the `www` variant is being retired too:

```js
export const CANONICAL_ALIASES = ['https://www.new-domain.com'];
```

Then `npm run test && npm run build`, and confirm `dist/index.html`,
`dist/sitemap.xml` and `dist/robots.txt` all reference the new domain.

Note: while `PREVIOUS_SITE_URL` is set and `HOST_REDIRECTS_CONFIRMED` is
`false`, **`npm run build` fails on purpose** and prints the exact rules to add.
`npm run test` and `npm run dev` are unaffected, so you can keep working. This
is deliberate: Workers Static Assets ignores domain-level redirects in
`_redirects`, so a migration that deploys without the zone rule loses ranking
signal and nothing in the build output would say so.

### 2. Deploy

`npm run deploy` (builds, then `wrangler deploy`).

### 3. Add a 301 on the old domain — required

**This is the step that preserves ranking.** Without it you are asking Google to
transfer authority from nothing, and expect a drop.

It must be configured at **zone level on the old domain**, not in this repo.
Cloudflare Workers Static Assets does not support domain-level redirects in a
`_redirects` file — a rule whose source names another host is *silently
ignored*. The generated `dist/_redirects` therefore contains **no active rules
at all**, and `npm run build` **fails with the rules to add** until you set
`HOST_REDIRECTS_CONFIRMED = true`. That way this cannot be mistaken for a
working redirect.

To add the host redirect:

1. Keep the old domain as a Cloudflare zone. Do not remove it.
2. **Rules → Bulk Redirects → Single Redirect**:
   - Source: `https://old-domain.com/*`
   - Target: `https://new-domain.com/:splat`
   - Status: **301**
   - Wildcards on, dynamic URL off
3. Add a second rule for the bare apex: source `https://old-domain.com`,
   target `https://new-domain.com/`, status 301. Without it, `old-domain.com`
   itself 404s while `old-domain.com/services` redirects.
4. Repeat for the `www` variant if the old site used one.

The `www` → apex move on the **new** domain is the one case you might want as
two separate zone rules (or a Cloudflare Redirect Rule) rather than Bulk
Redirects, since it needs to run before the Worker.

Verify the whole path, including the bare apex and a nested route:

```sh
curl -I https://old-domain.com/            # expect 301 -> https://new-domain.com/
curl -I https://old-domain.com/services    # expect 301 -> https://new-domain.com/services
curl -I https://new-domain.com/services/   # expect a redirect -> https://new-domain.com/services
curl -I https://new-domain.com/services    # expect 200
```

A redirect chain, or a 302 instead of a 301, is the most common way a migration
silently fails. Use `curl -IL` to walk the full chain rather than trusting a
single hop.

### 4. Keep the old domain registered forever

Do not let the old domain lapse. If it is dropped and later re-registered by
someone else, the 301s disappear along with the ranking you were trying to
keep. Leave it on Cloudflare with the redirect rule in place indefinitely.

### 5. Tell Google about it

For each Search Console property (old and new):

1. **Settings → Search Console → Change of Address**. Add the new property,
   verify it, then submit the move. This is the step that actually moves
   signals in Search results; the 301s do the crawling, this does the
   reassignment.
2. Submit `https://new-domain.com/sitemap.xml` under **Sitemaps**.
3. **URL Inspection** the new homepage and a couple of key routes, then press
   **Request indexing**.
4. Update **Google Business Profile** and **Google Analytics** property
   settings to the new domain.

Expect a normal dip in impressions for a few weeks, then recovery. If the old
domain had little traffic there is no dip to worry about.

### 6. Update external references

Anything that links to the old domain should point at the new one:

- Google Business Profile, Justdial, Practo, Sulekha, IndiaMART and any other
  directory listing
- Social profiles (Facebook, Instagram bio links)
- `localBusinessSchema().hasMap` and `sameAs` in `src/config/site.js` /
  `src/components/SEO/SEO.jsx` if the maps link embeds the old host
- The `docwebapp` GitHub remote, if you rename the repository

## Previously a client-rendered SPA (now fixed)

This used to be a real limitation, and it is worth recording because it changes what a migration
needs to verify.

`wrangler.jsonc` set `assets.not_found_handling: "single-page-application"`, so every path returned
the same `index.html` with HTTP 200. That produced two defects:

1. **Crawlers that do not execute JavaScript** saw the home page's title, description and canonical
   on every URL — a site-wide duplicate-content problem.
2. **A URL that did not exist returned 200**, not 404. `robots.txt` `Disallow`ed `/404` and `/500`,
   but a blocked URL is never crawled, so its status code was never seen. Real 404 handling was
   impossible.

Both are fixed. `build/prerender.js` now writes one static HTML file per route, and
`not_found_handling` is `"404-page"`, so unknown paths get a real 404 while still booting React.

**What this means for a migration:** the redirect checks in step 3 are now meaningful. Previously a
crawler that did not run JS could not be told the difference between a moved page and the home page,
so it could not follow the 301 chain reliably. Verify after deploying:

```bash
curl -I https://new-domain.com/services      # expect 200, not a redirect
curl -I https://new-domain.com/nonexistent   # expect 404, was 200
curl -s https://new-domain.com/services | grep -o 'rel="canonical"[^>]*'
                                          # expect the new domain, on the page itself
```

That last check is the one that matters most after a move: the canonical must be served in the
static bytes, not only after hydration. See `docs/SEO.md` §2.
